# Reflection — LibraryMind

## Design Decisions

The decision that shaped everything downstream was routing both OpenAI and Anthropic through a single Amali gateway instead of wiring in two separate SDKs. It meant `OpenAIProvider` and `AnthropicAIProvider` could be thin, stateless adapters over one `call_gateway()` function, and the retry/backoff logic only had to be written once. The trade-off is that both providers share one API key and one HTTP client shape, so I lose any provider-specific request tuning — an acceptable cost for a project where the point was demonstrating resilient fallback, not maximizing per-provider features.

For the RAG engine, I made the relevance threshold a configurable setting (`RAG_RELEVANCE_THRESHOLD`, default `0.4`) rather than a hardcoded constant, because I kept re-tuning it during development and didn't want to touch code every time. I also added refusal-phrase detection on top of the distance filter: even when ChromaDB returns results above the threshold, the model itself sometimes still says "I couldn't find anything relevant" if the match is topically close but not actually useful. Without stripping sources in that case, the API would return an answer that says "no" alongside a sources list that implies "yes" — an inconsistency a patron would notice immediately.

The chatbot deliberately does *not* reuse the RAG engine's cache. `rag_engine.query()` caches by question text alone, which is correct for stateless Q&A but wrong for a conversation — it would mean two different users asking the same opening question could end up served each other's cached context. Bypassing that cache in `chat_service.py` cost a small amount of duplicated retrieval logic, which I accepted over the alternative of silently leaking conversation state between users.

The last significant decision was architectural rather than functional: I originally had every service (`RAGEngine`, `ChatService`, `ClassificationService`, `SummarisationService`) call `build_service()` independently, so the app was constructing four separate `ResilientAIService` instances that all resolved to an identical provider order. I refactored this into a single shared instance built once and injected into all four — the same pattern I was already using for `cache`, `rate_limiter`, and `usage_tracker`. It didn't change behavior, but it removed redundant object construction and made the dependency-injection intent explicit instead of accidental.

## Challenges

The most persistent challenge was distance-vs-similarity confusion with ChromaDB. It returns cosine *distance* (0 = identical), not similarity, and I initially tuned my threshold as if higher meant "more relevant" — which silently inverted my filtering logic and let irrelevant books through while excluding good matches. I fixed it by writing the inversion explicitly (`relevance_score = 1 - distance`) and left a comment on the class itself so I wouldn't make the same mistake again after a week away from the code.

Getting classification and summarisation to return parsable JSON reliably was the other recurring friction point. Both providers, when asked for structured output, would sometimes wrap the response in ```` ```json ```` fences despite the prompt explicitly saying not to. I solved it with a small regex-based fence-stripper shared by both services, and made sure a malformed response raised a descriptive `ValueError` with the raw text attached, rather than failing silently — that turned "the classifier is broken" into "here's exactly what the model returned and why it didn't parse."

## A Debugging Story

The most instructive debugging session wasn't in the application code at all — it was infrastructure. Partway through the project I tried to pull a `dev` branch a teammate had pushed, and `git fetch` failed with `SSL certificate problem: self signed certificate in certificate chain`. My first instinct was the common shortcut — `git config --global http.sslVerify false` — but that disables certificate verification entirely, which felt like the wrong fix for a problem I didn't yet understand.

Instead I checked what was actually happening: `netsh winhttp show proxy` showed no system-wide proxy, and a direct TLS handshake to GitHub from a different shell context came back clean with GitHub's real certificate. That told me the interception wasn't a permanent misconfiguration in the repo or my machine's trust store — it was specific to whatever network path that one terminal session was using at that moment, most likely a VPN or campus network doing HTTPS inspection. The actual fix, if it recurs, is `git config --global http.sslBackend schannel`, which tells Git for Windows to trust the same certificate store Windows and the browser already trust, instead of its own bundled CA file — correct and safe, versus disabling verification, which is neither.

## Extensions Attempted

Beyond the core spec, I added: a configurable RAG relevance threshold instead of a fixed constant, refusal-phrase detection to keep source citations consistent with the model's actual answer, CORS middleware and full OpenAPI tag descriptions for Swagger/ReDoc, and a test suite that grew well past the "optional" bar in the spec — 135 tests covering provider fallback, cache degradation, rate-limit boundaries, RAG relevance filtering, conversation isolation, and JSON parsing edge cases. I also wrote both an HTTP-level smoke test and a provider-level integration test as separate scripts, since they exercise different failure modes and I wanted to be able to run the cheap one (`smoke_test_api.py`) without burning API budget on every check.
